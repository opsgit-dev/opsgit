How it works

Four steps, all of them in git

01

Write a flag

One JSON file per flag in flags/. Rules, rollouts, segments, expiry, and an owner. Your editor autocompletes it from the schema.

02

Open a pull request

The action validates every file, runs your fixtures, and posts a plain-English preview: what changed, for whom, and by how much.

03

Merge

The flags are compiled into a Worker and deployed to your Cloudflare account. Global in seconds. No database to warm up.

04

Evaluate

Servers download the bundle once and evaluate in-process. Browsers and apps call the Worker with a client key that never sees a rule.

The pull request

A flag change reads like a flag change

The preview comment is written for the reviewer, not the machine. Enabled or not, who it targets, what percentage, and whether anything expires. If a fixture fails, the check fails.

Deterministic rollouts

A user bucketed in at 25% stays in at 50%. Hashing is MurmurHash3 over the flag key and user id.

First match wins

Rules are evaluated top to bottom, conditions are ANDed. The comment tells you which rule a test user hit.

Fixtures

Files in tests/ pin an expected value for a context. They run on every PR.

Stale flags

A weekly issue lists flags past their expiry or untouched for 90 days, with the owner tagged.

What's in the box

Everything a flag system needs. Nothing it doesn't.

Percentage rollouts

Bucket by user id, account id, or any attribute you name. Sticky across deploys and across flags.

Segments

Name a group once in segments/, reference it from any rule. Beta testers, internal staff, a customer on a special plan.

Semver targeting

Force an upgrade below 2.3.0, or ship a feature only to builds that can handle it. Prerelease tags compare correctly.

Expiry and ownership

Every flag can carry an owner and an expiry date. The weekly stale-flag issue makes cleanup someone's job.

Two kinds of keys

Server keys read the whole bundle. Client keys can only evaluate, only see flags marked client: true, and never learn a rule name.

Edge native

ETag caching, 304s for unchanged bundles, per-key rate limits on client traffic, and geo attributes filled in from Cloudflare when you don't send them.

Security

Your targeting rules are yours

Most flag services hand the full rule set to every browser that asks. opsgit splits keys by role so that the public side of your app can only ask one question: what is the value for this user.

  • Flags are server-only unless you opt them in with client: true.
  • Keys are stored hashed and compared in constant time.
  • Client traffic is rate limited per key and IP at the data centre.
  • Request bodies are capped and contexts are scalar-only.
  • The GitHub Action is pinned to commit hashes, and so are its own dependencies.
